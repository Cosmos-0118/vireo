[A1] Persistent WebGL2 Contexts & Blinking Cursors on Hidden Terminals (CRITICAL)
  Where:
    - frontend/src/components/usePtyTerminal.ts:129-138, 214-229, 366
    - frontend/src/components/TerminalPanel.tsx:80, 91-101, 471-480
    - frontend/src/App.tsx:1145, 1916-1949
  What is happening:
    - Once the terminal dock has been opened once (terminalMountedRef.current = true),
      <TerminalPanel> stays mounted forever even when collapsed (className="hidden").
    - Inactive terminal tabs are hidden with style={{ display: active ? 'block' : 'none' }},
      keeping every tab's xterm Terminal instance and WebglAddon alive indefinitely.
    - tryWebgl() attaches new WebglAddon() and NEVER disposes it when active === false
      or when the terminal panel is hidden, with no cap on concurrent WebGL contexts.
      Each WebGL2 context pins D3D11/ANGLE surfaces, glyph texture atlases, and
      command buffers in msedgewebview2.exe gpu-process.
    - cursorBlink: true is unconditionally enabled on ALL terminals (including hidden
      tabs, collapsed terminal dock, and minimized/occluded windows), keeping
      xterm's blink timer and WebGL compositor repaints active forever.
    - This directly explains why live Vireo (3 terminals) burned 9.84% of a CPU core
      at idle (8.12% in gpu-process + 1.72% in renderer) while fresh Vireo (0
      terminals) had 0.00% gpu-process idle CPU.
    - Scrollback is set to 5,000 lines for agent tabs and 3,000 lines for shell tabs
      (large typed-array cell/attribute buffers per tab).
    - Also in usePtyTerminal.ts:366: window.setTimeout(sendAck, 50) is scheduled on
      EVERY binary WebSocket frame without coalescing or cancelling in teardown().
  How to optimize:
    1. Enforce at most 1 active WebglAddon across the app: dispose WebglAddon
       whenever !active || !showTerminal || document.hidden, and re-attach on
       activation.
    2. Set term.options.cursorBlink = false whenever !active || !showTerminal ||
       document.hidden.
    3. Lower default scrollback (e.g., 1,000-1,500 for shells, 2,500 for agents)
       or make it configurable.
    4. Coalesce the 50 ms sendAck timer into a single ref and clear it in teardown().
  Expected gain:
    - Idle CPU: 9.84% of 1 core -> <0.5-1.0% of 1 core.
    - GPU process RAM: -15 to -40+ MB when multiple terminal tabs are open.

[A2] Spawned PowerShell 7 (pwsh.exe) Footprint & 30-Minute Detached PTY Retention
  Where:
    - backend/src/pty.rs:24, 32, 655-662, 722-725, 784-797, 839-845, 868-900
    - frontend/src/components/TerminalPanel.tsx:271-293
  What is happening:
    - On Windows, pty.rs prefers pwsh.exe (PowerShell 7 / .NET Core runtime).

    - Switching workspacePath in TerminalPanel.tsx does not reset the tabs state.

       or circular slice) capped at 512 KiB - 1 MiB (or shrink_to after drain).
    3. Lower DETACHED_TTL (e.g. 2-5 minutes) and cap total detached PTY sessions

================================================================================
3. ARCHITECTURAL REALITY CHECK: WHY VIREO IS ~500 MB WS AND THE WEBVIEW2 FLOOR
================================================================================

Even after fixing EVERY item above, it is important to set realistic expectations
for WebView2 on Windows:

  Measured WebView2 baseline (fresh launch, 0 terminals, lean flags):
    - Working Set:    ~480 MB (7 processes: Rust host + 6 msedgewebview2.exe)
    - Private WS:     ~168 MB
    - Private Commit: ~254 MB

That ~170 MB Private WS / ~255 MB Private Commit floor is Chromium's multi-process
architecture (Browser + GPU/ANGLE + V8/Blink Renderer + Network + Storage +
Crashpad). You CANNOT shrink a WebView2 app to 30-50 MB RAM.

What optimization WILL achieve realistically on WebView2:
  - Idle CPU (with 3 terminals open):  ~9.8% of 1 core  -->  <0.5-1.0% of 1 core
  - Active multi-terminal session RAM: ~831 MB WS / 402 MB Commit -->
                                       ~480-550 MB WS / ~250-300 MB Commit
                                       (bigger savings as session ages / tabs grow)
  - Cold backend startup latency:      ~625 ms          -->  ~150-250 ms
  - /api/git/status latency:           ~440 ms          -->  ~50-80 ms
  - /api/git/branches latency:         ~381 ms          -->  ~60-90 ms
  - /api/agent/cli-tools latency:      ~370 ms          -->  <1 ms (cached)
  - vireo.exe binary size:             25.28 MiB        -->  ~14-16 MiB
  - vx.exe binary size:                 7.16 MiB        -->  ~5.5-6.0 MiB
  - frontend/dist asset size:           3.06 MiB        -->  ~1.6-2.0 MiB
                                       (or ~1.0-1.4 MiB if single terminal engine)

If the long-term goal were ever a truly "tiny" (<80 MB total RAM) desktop app,
that would require replacing WebView2/Chromium with a native GPU UI toolkit
(e.g. GPUI, Iced, Slint, or WinUI/DirectWrite) -- a full frontend rewrite rather
than an optimization pass.
